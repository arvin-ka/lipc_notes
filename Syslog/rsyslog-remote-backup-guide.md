# 📡 راهنمای جامع و کاربردی: ارسال لاگ‌های سیستم به Backup Server ریموت با RSYSLOG

در شبکه‌های سازمانی و محیط‌های عملیاتی، ذخیره کردن لاگ‌ها فقط روی خود سرور محلی (Local Server) یک ریسک بزرگ محسوب می‌شود. اگر سرور اصلی دچار خرابی دیسک، نفوذ هکرها یا کرش کامل شود، تمامی لاگ‌های ثبت‌شده از بین خواهند رفت و امکان عیب‌یابی یا تحلیل خطاهای امنیتی (Forensics) ناپدید می‌شود.

حل این چالش با ارسال مرکزی لاگ‌ها به یک Backup Server ریموت (Remote Logging) انجام می‌شود. در این داکیومنت، تمام مفاهیم، پروتکل‌ها، روش‌های ارسال، تنظیمات سمت کلاینت (Client/Sender) و سرور (Server/Receiver)، فیلترها و نکات امنیتی به‌صورت گام‌به‌گام و به زبان ساده توضیح داده شده است.

## ۱. چرا به سرور ریموت لاگ (Remote Log Server) نیاز داریم؟

ارسال لاگ‌ها به یک سرور ریموت سه مزیت کلیدی ارائه می‌دهد:

* امنیت بالا (Security & Anti-tampering): اگر هکری به سرور اصلی نفوذ کند، اولین کاری که انجام می‌دهد پاک کردن فایل‌های لاگ در مسیر ``/var/log`` است تا ردپای خود را بپوشاند. اگر لاگ‌ها لحظه‌ای به سرور ریموت منتقل شوند، مهاجم نمی‌تواند لاگ‌های ارسال‌شده را پاک کند.
* عیب‌یابی مرکزی (Centralized Troubleshooting): تیم‌های پشتیبانی و DevOps به جای لاگین کردن به ده‌ها سرور مختلف، تمام لاگ‌ها را در یک مرکز پایش می‌کنند.
* مدیریت فضای دیسک (Disk Space Optimization): سرورهای عملیاتی نیازی به ذخیره لاگ‌های قدیمی چندماهه ندارند و می‌توان این لاگ‌ها را روی پشتیبان ریموت آرشیو کرد.

## ۲. مقایسه پروتکل‌های انتقال: UDP در مقابل TCP

برای ارسال لاگ‌ها در پروتکل Syslog از دو پروتکل لایه انتقال بهره گرفته می‌شود:

| ویژگی | پروتکل UDP (پورت ۵۱۴) | پروتکل TCP (پورت ۵۱۴) | 
| :--- | :--- | :--- |
| سرعت و بار سیستم | بسیار سریع با مصرف منابع حداقل | کمی کندتر به دلیل Handshake و کنترل جریان |
| قابلیت اطمینان (Reliability) | بدون تضمین: پیام‌ها ممکن است در شبکه گم شوند | تضمین‌شده: اگر بسته‌ای گم شود، دوباره ارسال می‌شود |
| وضعیت اتصال (Connection) | Connectionless (بدون برقرار ساختن نشست) | Connection-oriented (دارای نشست فعال) |
| کاربرد مناسب | شبکه‌های داخلی بسیار پایدار با ترافیک لاگ حجیم | ارسال لاگ‌های حساس، مالی، امنیتی و بسترهای اینترنت |

## ۳. معماری کلی ارتباط کلاینت و سرور

```
─────────────────────────┐               UDP / TCP (Port 514)              ┌─────────────────────────┐
│     Client / Sender     │ ──────────────────────────────────────────────> │ Remote Log Server (Recv)│
│  (192.168.1.50)         │                                                 │     (192.168.1.100)     │
│  - App Logs / Syslog    │                                                 │  - /var/log/remote/     │
└─────────────────────────┘                                                 └─────────────────────────┘
```

## ۴. تنظیمات سمت سرور (Remote Log Server - دریافت‌کننده)

سرور ریموت باید طوری تنظیم شود که روی پورت ۵۱۴ (UDP یا TCP) به پیام‌های ورودی گوش دهد و آن‌ها را بر اساس آی‌پی کلاینت یا نام سیستم (Hostname) در فولدرهای مجزا ذخیره کند.

### گام اول: ویرایش فایل ``/etc/rsyslog.conf``

فایل کانفیگ اصلی را در سرور باز کنید:

``sudo nano /etc/rsyslog.conf``

### گام دوم: فعال‌سازی ماژول‌های دریافت (Input Modules)

خطوط مربوط به UDP یا TCP را از حالت کامنت خارج کنید (علامت ``#`` را بردارید):

برای دریافت روی UDP:

```
module(load="imudp")
input(type="imudp" port="514")
```

برای دریافت روی TCP:

```
module(load="imtcp")
input(type="imtcp" port="514")
```

### گام سوم: جداسازی لاگ‌های دریافت شده بر اساس کلاینت‌ها (Template)

اگر تمامی لاگ‌ها در فایل‌های استاندارد مثل ``/var/log/syslog`` ذخیره شوند، لاگ‌های سرور اصلی با کلاینت‌ها مخلوط می‌شوند. برای جلوگیری از این کار، یک الگو (Template) تعریف می‌کنیم تا برای هر کلاینت یک پوشه جداگانه بسازد:

```
# تعریف قالب برای مرتب‌سازی لاگ‌های ریموت
$template RemoteLogs,"/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log"
*.* ?RemoteLogs
& stop
```

توضیحات الگوی فوق:

* ا ``%HOSTNAME%``: اسم کلاینت فرستنده لاگ را به عنوان نام پوشه قرار می‌دهد.
* ا ``%PROGRAMNAME%``: سرویسی که لاگ را تولید کرده (مثل sshd یا cron) به عنوان نام فایل استفاده می‌شود.
* ا ``& stop``: پس از پردازش این قانون، پردازش لاگ متوقف می‌شود تا نسخه دیگری از آن درون لاگ‌های محلی خودِ سرور ذخیره نشود.

### گام چهارم: ری‌استارت سرویس RSYSLOG

``sudo systemctl restart rsyslog``

## ۵. تنظیمات سمت کلاینت (Client - ارسال‌کننده)

روی سروری که قصد دارید لاگ‌های آن به Backup Server منتقل شود، تنظیمات زیر را انجام دهید.

سینتکس عمومی ارسال لاگ در RSYSLOG:

* علامت ``@`` یک‌تایی: ارسال با پروتکل UDP
* علامت ``@@`` دو‌تایی: ارسال با پروتکل TCP

ارسال تمامی لاگ‌ها با UDP و TCP

یک فایل کانفیگ جدید در مسیر ``/etc/rsyslog.d/remote-send.conf`` ایجاد کنید:

``sudo nano /etc/rsyslog.d/remote-send.conf``

مثال ۱: ارسال کل لاگ‌های سیستم با پروتکل UDP

``*.* @192.168.1.100:514``

مثال ۲: ارسال کل لاگ‌های سیستم با پروتکل TCP

``*.* @@192.168.1.100:514``

### ارسال لاگ‌های خاص (فیلتر بر اساس Facility و Priority)

نیازی نیست همواره تمامی لاگ‌ها ارسال شوند؛ می‌توانید فقط لاگ‌های حساس را فیلتر کنید:

مثال ۱: فقط ارسال لاگ‌های احراز هویت و ورود/خروج (``auth``, ``authpriv``)

``auth,authpriv.* @@192.168.1.100:514``

مثال ۲: ارسال تمامی لاگ‌های با سطح اهمیت بالا (Critical, Alert, Emergency)

``*.crit;*.alert;*.emerg @@192.168.1.100:514``

مثال ۳: ارسال لاگ‌های وب‌سرور یا سرویس‌های سفارشی به همراه استثنا کردن لاگ‌های Cron

``*.* ; cron.none @@192.168.1.100:514``

پس از اعمال تغییرات، سرویس کلاینت را ری‌استارت کنید:

``sudo systemctl restart rsyslog``

## ۶. استفاده از Action Queue برای جلوگیری از قطعی شبکه

اگر ارتباط شبکه بین کلاینت و سرور ریموت برای چند دقیقه یا چند ساعت قطع شود، تکلیف لاگ‌ها چه می‌شود؟ اگر از TCP استفاده کنید، لاگ‌ها بلافاصله از دست می‌روند مگر اینکه حافظه میانجی (Queue) فعال شده باشد.

با کانفیگ زیر، در صورت قطعی شبکه، لاگ‌ها روی دیسک کلاینت ذخیره شده و پس از وصل شدن مجدد شبکه، به‌صورت خودکار به Backup Server ارسال می‌گردند:

```
# ایجاد صف ذخیره‌سازی محلی در صورت قطع ارتباط شبکه
$ActionQueueFileName fwdRule1       # نام فایل‌های صف روی دیسک
$ActionQueueMaxDiskSpace 1g         # حداکثر حجم مجاز صف (۱ گیگابایت)
$ActionQueueSaveOnShutdown on       # ذخیره صف روی دیسک در صورت خاموش شدن کلاینت
$ActionQueueType LinkedList         # مدیریت حافظه پویا
$ActionResumeRetryCount -1          # تلاش نامحدود برای وصل مجدد به سرور

# دستور اصلی ارسال لاگ
*.* @@192.168.1.100:514
```

## ۷. امن‌سازی ارتباط با TLS/SSL (ارسال رمزشده لاگ‌ها)

پیام‌های Syslog به‌صورت متن ساده (Plaintext) در شبکه منتقل می‌شوند. اگر لاگ‌ها از طریق بستر اینترنت یا شبکه عمومی منتقل می‌شوند، باید از ماژول ``gtls`` استفاده کنید تا لاگ‌ها رمزنگاری شوند.

### ۱. نصب ماژول TLS برای RSYSLOG:

```
sudo apt install rsyslog-gtls    # در سیستم‌های برپایه دبیان/اوبونتو
# یا
sudo dnf install rsyslog-gtls    # در سیستم‌های برپایه ردهت/راکی لینوکس
```

### ۲. پیکربندی کلاینت جهت ارسال رمزشده (TLS):

```
# بارگذاری ماژول TLS
module(load="omfwd")

# تنظیم گواهی‌های امنیتی (CA Certificate)
$DefaultNetstreamDriver gtls
$DefaultNetstreamDriverCAFile /etc/ssl/certs/ca-cert.pem
$ActionSendStreamDriverAuthMode x509/name
$ActionSendStreamDriverPermittedPeer logserver.example.com
$ActionSendStreamDriverMode 1 # فعال‌سازی حالت TLS

# ارسال رمزشده روی پورت ۶۵۱۴
*.* @@logserver.example.com:6514
```

## ۸. تست، عیب‌یابی و راست‌آزمایی ارسال لاگ‌ها

پس از انجام تنظیمات، با استفاده از روش‌های زیر می‌توانید از صحّت کارکرد سیستم مطمئن شوید:

### ۱. ارسال لاگ تست از کلاینت با دستور logger

روی کلاینت دستور زیر را اجرا کنید تا یک لاگ سفارشی ایجاد شود:

``logger -p auth.info "TEST_LOG: Testing remote syslog server connection"``

### ۲. بررسی فایل‌های لاگ روی سرور ریموت

روی سرور ریموت چک کنید که آیا پوشه و فایل لاگ جدید برای کلاینت ساخته شده است یا خیر:

```
ls -la /var/log/remote/
cat /var/log/remote/<Client-Hostname>/auth.log
```

### ۳. بررسی شنود پورت‌ها با ``ss`` یا ``netstat``

روی سرور بررسی کنید که آیا RSYSLOG به پورت ۵۱۴ گوش می‌دهد:

``sudo ss -tulpn | grep 514``

1. تست اتصال پورت از کلاینت به سرور
``بررسی لایه شبکه``

روی کلاینت با ابزار nc (Netcat) از باز بودن پورت ۵۱۴ سرور مطمئن شوید:

``nc -zvw3 192.168.1.100 514``

2. تست ارسال پیام مستقیم
``تست لایه برنامه``

یک پیام دستی از کلاینت روی پورت TCP ارسال کنید:

``echo "Test Message" | nc 192.168.1.100 514``

**نکته مهم فایروال (Firewall)**

در صورت عدم دریافت لاگ‌ها، حتماً فایروال سرور (UFW یا Firewalld) را بررسی کنید و اجازه عبور ترافیک پورت ۵۱۴ روی UDP/TCP را صادر نمایید:

``sudo ufw allow 514/tcp``
``sudo ufw allow 514/udp``
